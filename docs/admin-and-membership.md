# 운영 웹과 회원 권한 설계 제안

2026-09-24: 설계 문서이며 관리자 웹·구독 테이블·결제 처리를 배포한 상태는 아니다. 이번 구현은 신고 증거 보완(004)과 기존 운영 CLI 표시까지다.

## 1. 관리자 웹은 앱과 분리, DB는 기존 권한 경계 재사용

별도 관리자 웹 앱과 서버 API를 두되, 처음부터 별도 물리 서버/별도 사용자 DB가 필요한 것은 아니다. 별도 배포 단위로 운영하고 같은 Supabase의 제한된 운영 RPC를 서버에서 호출한다. 앱 사용자 API와 운영 API의 인증/권한은 분리한다.

- 브라우저는 운영자 세션만 가진다. service role 키는 서버 비밀 저장소에만 둔다.
- 서버가 서명·만료·인증 공급자를 검증한 세션의 사용자 ID를 운영자 ID로 사용한다. 브라우저가 보내는 `operator_id`를 신뢰하지 않는다. 현재 RPC의 `p_operator_id`는 이미 검증된 서버에서만 채워야 한다.
- 기존 `public.operators`와 `private.require_operator`를 확장한다. 새 `profiles.role='admin'` 검사를 별도로 만들어 이중 권한 체계를 만들지 않는다.
- 매 요청에서 활성 여부와 작업 권한을 확인한다. 오래된 JWT의 admin claim만 믿으면 권한 회수가 지연될 수 있으므로 DB 권한을 최종 판정으로 둔다. MFA·짧은 세션·CSRF 방어·속도 제한·중요 작업 재확인을 추가한다.
- 초기에는 등록 운영자만 사용하고, 팀이 커지면 `support`(최소 상태 조회), `moderator`(신고 증거/제재), `admin`(운영자 권한 관리)로 역할과 허용 작업을 나눈다. `viewer`라도 신고 증거 전체가 자동 허용되는 것은 아니다.
- 정지·해제·권한 부여·보상성 이용권 부여와 민감 증거 상세 조회는 행위자/대상/사유/결과를 감사 기록에 남긴다. 증거를 로그 본문에 복제하지 않는다. 현재 감사 범위는 확정 조치와 제재 이력 조회이므로 상세 증거 열람 감사는 추가 구현 대상이다.
- 운영자를 운영자로 만드는 공개 가입/프로필 수정 경로는 없다. 첫 운영자 등록은 서버 전용 운영 절차, 이후 권한 위임/회수는 별도 권한을 가진 운영자가 처리한다.

## 2. 권장 페이지

| 페이지 | 초기 범위 | 기본적으로 제외할 정보 |
| --- | --- | --- |
| 요약 | 가입/활성/완료 러닝 집계, 미처리 신고, 실패 작업 수 | 개인의 경로·정확한 러닝 시각 |
| 신고·안전 | 유형/대기 기간, 서버 증거, 제재 이력, 조치·기각·이의제기 | 신고자 신원 기본 노출, 미신고 대화 무제한 검색 |
| 사용자 지원 | 내부 ID로 최소 상태 조회, 인증 완료 여부, 탈퇴 처리 상태 | 실제 인증 원문, CI/DI, 원본 GPS |
| 구독·결제 | 구독 상태/유효기간, 환불·갱신 실패 동기화 상태 | 카드 번호, 구매 토큰 원문 노출 |
| 러닝 처리 | 검증 큐/재시도/실패 원인 집계 | 사용자별 실시간 지도 |
| 알림·데이터 처리 | 푸시 실패/receipt, 위치 파기/계정 삭제 작업 지연 | 메시지 본문·푸시 토큰 원문 |
| 운영 권한·감사 | 운영자 활성/역할, 중요 작업 감사 내역 | service role 키 |

기존 신고 큐 RPC는 증거까지 반환하므로 전체 운영 요약/일반 지원 페이지에 그대로 쓰지 않는다. 목록용 최소 응답과 권한 있는 상세 증거 조회를 분리하는 후속 RPC가 필요하다. `show` CLI는 상태별 최대 200건 큐에서 찾는 방식이므로 웹용 개별 조회/페이지네이션도 별도로 구현한다.

## 3. 요금제와 운영 권한은 서로 다른 축

`user_type = normal | premium | admin` 한 컬럼은 사용하지 않는다. 운영자이면서 프리미엄을 구매한 사용자, 프리미엄이지만 정지된 사용자를 제대로 표현할 수 없기 때문이다.

| 영역 | 기준 데이터 | 예시 |
| --- | --- | --- |
| 기본 계정 | 기존 auth/profiles | 닉네임, 가입 상태, 성인 검증 |
| 구독 | 새 서버 전용 subscriptions | 공급자, 상품, 상태, 기간, 자동 갱신 |
| 실제 유료 이용 자격 | subscriptions/기간형 이용권에서 중앙 함수로 파생 | free / premium, 이용 종료 시각 |
| 운영 권한 | 기존 operators 확장 | support / moderator / admin, active |
| 안전 제한 | 기존 moderation_actions | 요청 제한, 정지, 해제 |

구독에는 최소 다음 정보가 필요하다.

- `user_id`, `provider`(Apple/Google 등), `product_id`, 공급자 구독 식별자(서버 전용)
- `started_at`: 해당 구독 시작일. 재가입은 별도 구독 이력으로 취급한다.
- `current_period_start`, `current_period_end`: 현재 결제 회차의 이용 기간
- `status`: active / grace / on_hold / expired / revoked 등 공급자 상태를 정규화하되 원래 상태도 서버에 보존
- `auto_renew_enabled`, `cancelled_at`: 갱신 취소와 즉시 이용 만료를 구분
- `next_billing_at`: 공급자가 확인해 준 다음 결제 **예정** 시각. 미확정/자동 갱신 해제라면 null. 앱에서 시작일+30일로 계산하지 않는다.
- `last_verified_at`: 마지막 공급자 확인 시각. 실패·지연을 운영 화면에서 식별

별도 `subscription_events`에 공급자 이벤트 ID(고유 제약), 처리 결과와 순서를 기록해 중복 알림·순서 역전을 처리한다. 알림 도착만으로 권한을 주지 않고 서명/구매와 사용자 연결을 서버에서 검증한다. 하나의 구매를 여러 계정에 중복 귀속하지 않는다. 환불·취소·유예·보류·만료·복원은 공급자 최신 상태를 다시 확인한다.

운영자 프로모션은 결제 이력을 위조하지 않고 `entitlement_grants` 같은 별도 기간형 이용권으로 처리한다. 사유·만료일·부여자·회수 이력을 남기고 결제 예정일은 만들지 않는다.

앱에는 본인의 `plan`, `valid_until`, `auto_renew_enabled`, `next_billing_at` 등 최소 요약만 제공한다. 일반 사용자가 `is_premium`, 운영 역할, 구독 날짜를 직접 변경하지 못하게 한다. JWT claim은 화면 편의용 보조 신호로만 두고 실제 유료 API는 같은 서버 판정을 호출한다.

유료 이용권이 있어도 상호 수락·성인 검증·차단·제재를 우회하지 않는다. 무료 사용자에게도 기록 저장·삭제·공개 범위 변경·신고·차단·안전 가이드는 그대로 제공한다.

## 4. 신고 증거 구현 범위와 후속

004에서 신고 당시 조회 가능한 소개/성향을 기존 안전 뷰로 복사한다. 신고 접수 자격은 `private.profile_report_allowed` 한 곳에 둔다. 현재 조회 대상 또는 친구/요청/수신 메시지/본인 차단/기존 신고 관계가 있으면 안전 신고가 가능하다. 차단 관계를 허용하는 것은 당시 내용을 보았다는 증명이 아니며, 현재 조회할 수 없으면 `snapshot_status=unavailable`로 남기고 본문을 읽지 않는다.

직접 reports INSERT/UPDATE와 증거 SELECT는 허용하지 않고, 본인 신고 접수 내역의 최소 컬럼만 조회 가능하다. 증거는 신고 RPC의 서버 복사로만 생성하고 기존 변경·삭제/계정 파기 정책을 유지한다. 캡처 시각은 증거 접수 시각이며 실제 러닝 시각이 아니다. 기존 신고의 빠진 소개를 현재 소개로 소급 채우지 않는다.

**남은 사항:** 사용자가 화면에서 본 뒤 신고 전에 바뀐 소개는 이번 방식으로 복구하지 못한다. 출시 전 private 프로필 버전 저장 + 실제 조회 이력에 묶인 버전 참조 + 신고 RPC 검증 + 보관 기간/파기 작업이 필요하다. 단순히 임의 version ID를 받아 과거 프로필을 조회하게 하면 안 된다. 보존 기간은 운영/개인정보 정책 확정 후 정하며 무기한 이력을 자동 저장하지 않는다. 신고 도배 제한과 차단만 한 임의 대상에 대한 신고 악용 방지도 별도 검토한다.

## 5. 구현 순서

1. 신고 증거 보완(이번 구현), 버전 기반 보존/열람 감사/목록·상세 분리.
2. 별도 관리자 웹의 로그인·MFA·권한 검사 → 신고 검토와 감사 화면.
3. 운영 상태 집계·검증/푸시/삭제 모니터링 페이지.
4. 유료 상품 확정 후 subscriptions/이용권/이벤트 처리와 앱 결제·복원 흐름.

참고: [Supabase RBAC](https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac), [RLS와 키 경계](https://supabase.com/docs/guides/database/postgres/row-level-security), [Google Play 구독 수명주기](https://developer.android.com/google/play/billing/lifecycle/subscriptions). Google은 알림 후 서버에서 최신 구독 상태를 조회하도록 안내한다. 실제 결제 도입 시 각 플랫폼의 당시 요구사항을 다시 확인한다.
